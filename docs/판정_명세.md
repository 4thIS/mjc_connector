# 판정 명세 — `evaluate_eligibility`

> 2026-10-18 초안 · 확정 아님. 구현 전 확정용이며, 테스트 담당이 이 문서만으로 테스트를 쓸 수 있게 한다.
> 표기: **[결정]** 팀장이 정함(2026-10-18) / **[제안]** 초안 값, 바꿔도 됨 / **[한계]** 이 설계가 보장하지 못하는 것
> 근거 설계: 판정은 AI가 아니라 코드가 한다. AI는 공지에서 조건을 뽑기만 하고, 서버가 인용 검증·날짜 계산·프로필 대조를 한다. 불확실하면 지어내지 않고 "확인 필요"로 답한다.

## 1. 함수 구조

```
evaluate(profile, extraction, body, today, posted_on=None) -> Verdict   # 순수 함수. 네트워크 없음. 테스트 대상
evaluate_eligibility(notice_id, profile, extraction)                    # MCP 도구. 본문과 작성일을 서버가 직접 가져오고 오늘 날짜(KST)를 넣어 evaluate 호출
```

- 판정 로직을 순수 함수로 분리해 `today`와 `body`를 테스트에서 직접 넣는다. [제안]
- 도구는 `get_notice`와 같은 방식으로 `notice_id`를 받아 서버가 본문을 다시 가져온다. 호스트 AI가 넘긴 본문은 쓰지 않는다. [제안]
- **위치**: 판정 코드는 이 리포(`mjc_connector`)의 파이썬 패키지 `mjc_connector`에 둔다. 공지 조회 같은 MCP 도구는 `hackathon_mjc_mcp`를 특정 커밋에 고정한 의존성으로 가져다 쓴다. 원격 진입점도 이 리포로 옮긴다. **[결정 2026-10-23]**
- **입력 형태**: `profile`·`extraction`은 Pydantic 모델(`Profile`, `Extraction`)로 받는다. MCP 입력 스키마와 필드 설명이 자동으로 만들어진다. 모델 검증에서 걸린 값(범위 밖 학년 등)도 도구가 `ToolError`로 바꿔 돌려주어 T18·T19·T24·T25의 오류 규칙을 지킨다. **[결정 2026-10-23]**
- **`posted_on`**: 공지 작성일. 선택 인자로 지금 시그니처에 넣는다. 날짜 연도 보완(3절 9번 C)에 쓰며, 실제로 쓰는지는 dh-11에서 확정한다. **[결정 2026-10-23]**
- **테스트**: 판정 함수를 구현하는 사람(팀장)이 7절 표의 테스트를 먼저 쓰고, 테스트 담당은 표와 대조해 빠진 케이스를 보강한다. **[결정 2026-10-23]**

## 2. 입력

**profile** — 호출 인자로만 받고 저장·로그·캐시하지 않는다.
- `department`: 정식 학과명(문자열). 약칭 정규화는 학과명 매칭 도구(아직 없음)의 몫이고 이 함수는 정식명만 받는다. 정식명 목록은 기존 `list_departments`의 정적 매핑이다. `extraction.departments`도 정식명이어야 한다.
- `grade`: 정수(1~4). 범위 밖이면 `ToolError`.
- `status`: 허용 값 `재학` / `휴학` / `졸업예정` 중 하나. 이 밖의 값은 `ToolError`. **[결정 2026-10-18]** 초기 목록이며 G3(공지 30건 라벨링) 결과를 보고 확정한다. `extraction.statuses`도 같은 값만 쓰고, 공지의 표현이 이 밖이면(복학생, 편입생 등) 호스트 AI가 옮기지 못해 `unknown`이 된다.

**extraction** — 호스트 AI가 공지에서 뽑은 값. 각 필드는 아래 형태다.

| 필드 | value | 설명 |
|---|---|---|
| `grades` | 정수 목록 또는 `"ANY"` 또는 null | 대상 학년 |
| `departments` | 학과명 목록 또는 `"ANY"` 또는 null | 대상 학과 |
| `statuses` | 문자열 목록 또는 `"ANY"` 또는 null | 대상 재학 상태 |
| `apply_start` | `YYYY-MM-DD` 또는 null | 신청 시작 |
| `apply_end` | `YYYY-MM-DD` 또는 null | 신청 마감(당일 포함) |
| `organizer` | `"school"` / `"external"` / null | 프로그램 운영 주체. 근거 표기 없음. 3절 11번에만 쓴다 |
| `other_conditions` | `{text, quote 또는 from_image}` 목록(기본 빈 목록) | 판정 범위 밖 자격 조건(나이·소득·성적·이전 수혜·혼인·거주지 등) |
| `images_checked` | true / false(기본) | 본문 이미지를 모두 읽고 대상을 확인했는지. 3절 11번에만 쓴다 |
| `refers_elsewhere` | `{quote 또는 from_image}` 또는 null | 대상·조건을 다른 공지나 별도 문서에서 보라고 적힌 문장. 3절 11번의 추정을 막는다 |

각 필드의 근거 표기는 다음 중 하나다.
- `quote`: 공지 본문 원문 인용(문자열)
- `from_image: true`: 이미지에서 읽은 값(인용 검증 불가)
- `"ANY"`(제한 없음)도 반드시 `quote`가 있어야 한다(예: "전 학년 대상"). 근거 없는 `"ANY"`는 인정하지 않는다. **[결정 2026-10-18]**
- `"ANY"`는 `quote`가 본문에서 확인될 때만 인정한다. `from_image: true`만 있는 `"ANY"`(이미지에서 읽은 "제한 없음")도 인정하지 않는다. **[결정 2026-11-06]**

value가 null이면 "공지에 적혀 있지 않다(못 찾았다)"는 뜻이다. 학년·학과·재학 상태의 null은 3절 11번에 따라 해석한다. 목록은 값이 1개 이상이어야 하며, 빈 목록은 입력 오류로 거절한다. **[결정 2026-11-06]**

## 3. 필드별 평가

각 필드는 `result ∈ {match, mismatch, unknown, not_yet}`과 `source ∈ {text_quote, image_read, missing, unverified_quote, unrecognized_value, assumed}`를 낳는다.

1. value가 null → `unknown` / `missing`. 단 학년·학과·재학 상태는 11번을 먼저 적용한다
2. `quote`가 있고 본문에 있음 → 값 사용, `source = text_quote`
3. `quote`가 있는데 본문에 없음 → 값을 믿지 않고 `unknown` / `unverified_quote`
4. `from_image: true` → 값 사용, `source = image_read`. `quote`가 본문에 없어도 `from_image: true`면 3이 아니라 4를 적용한다. **[결정 2026-11-06]**
5. 값은 있는데 `quote`도 `from_image`도 없음(`"ANY"` 포함) → 3과 같이 `unknown` / `unverified_quote`. `"ANY"`는 `from_image`가 있어도 본문 인용이 없으면 같다(2절)
6. `"ANY"`에 `quote`가 있고 본문에 있음 → `match` / `text_quote`
7. 인용 비교는 **공백·줄바꿈을 모두 제거하고** NFKC 정규화한 뒤 부분 문자열로 비교한다. [제안] 공백만 있는 인용은 근거가 없는 것으로 본다(정규화하면 빈 문자열이 되어 어디에나 들어 있게 되므로).
8. 날짜: `apply_end < today` → `mismatch`. `apply_end == today`는 `match`(당일 포함). `apply_start > today` → `not_yet`(판정에 영향 없음, 사유에만 표시). [제안]
9. **날짜 교차 검증 — 목표는 C, 안 되면 B [결정 2026-10-18]**
   - **C(목표)**: 서버가 본문에서 날짜 표현을 직접 추출해 후보 집합을 만들고, `apply_start`·`apply_end`의 월·일이 그 집합에 있어야 한다. 없으면 3과 같이 `unknown` / `unverified_quote`. 연도가 본문에 없으면 공지 작성일의 연도(작성일 이전 날짜면 다음 해)를 쓴다. [제안]
   - **B(후퇴)**: C를 못 쓰게 되면, 인용 문자열에 값의 월·일 숫자가 들어 있어야 한다(`11월 6일`, `11.6`, `11/06`, `2026-11-06` 허용). 없으면 같은 처리.
   - **후퇴 기준**: 날짜 추출기가 G3로 라벨링한 텍스트 공지에서 정답 날짜를 후보에 포함하는 비율이 임계값에 못 미치면 B로 한다. 임계값은 G3 결과를 본 뒤 팀장이 정한다. [제안: 기준 방식만, 값은 미정]
   - C·B 모두 `from_image` 값에는 적용하지 않는다(본문에 근거가 없다). 인용(`quote`)이 있는 날짜에만 적용한다.
   - 학년 숫자 교차 검증은 하지 않는다("2학년 이상" 같은 표현 때문). [결정]
10. `departments`·`statuses` 값이 허용 목록(정식 학과명 목록, status enum) 밖이면 값을 사용하지 않고 `unknown` / `unrecognized_value`. 인용 검증보다 먼저 적용한다. 정식 학과명 목록은 기존 `list_departments`의 정적 매핑을 쓴다. [제안]
11. **적혀 있지 않은 대상의 해석 [결정 2026-11-21]** — value가 null이고 근거(`quote`·`from_image`)도 없을 때만 적용한다. 인용이 확인되지 않은 값(3·5번)이나 허용 목록 밖 값(10번)은 대신 채우지 않는다. value가 null인데 근거가 있으면 대상이 적혀 있지만 값으로 옮기지 못한 것이므로 `unknown` / `unrecognized_value`다. 그 인용이 본문에 없으면 3번과 같이 `unknown` / `unverified_quote`다. 공백만 있는 인용은 근거로 보지 않는다.
    - 규칙 1: `grades`·`departments`가 null → 전체 대상(`ANY`)으로 보고 `match` / `assumed`. evidence에 "적혀 있지 않아 전체 대상으로 봤습니다(추정)"를 쓴다.
    - 규칙 2: `statuses`가 null이고 `organizer`가 `school` → 재학생 대상으로 보고, 프로필이 재학이면 `match` / `assumed`, 아니면 `mismatch` / `assumed`. `organizer`가 `external`이나 null이면 1번(`unknown` / `missing`) 그대로다. [제안: 교내 판단을 `organizer` 필드로 받는 방식]
    - `assumed`의 `mismatch`는 "불가"가 아니라 "확인 필요"다(4절 1·2번: text_quote의 mismatch만 불가).
    - **본문 이미지가 있는 공지 [결정 2026-11-26]**: 서버는 이미지를 읽지 못하지만 호스트 AI는 읽을 수 있다. AI가 이미지를 모두 읽고 `images_checked: true`로 넘기면 추정하되, 이미지에 기댄 결과이므로 신뢰도는 `image_unverified`이고 evidence에 원본 이미지 확인을 덧붙인다(4절 5번의 이미지 유래 "가능"과 같은 취급).
    - **추정하지 않는 경우 [결정 2026-11-26]**: 공지에 첨부 파일이 있거나(판정은 첨부를 읽지 않는다) `refers_elsewhere`의 근거가 본문에서 확인되거나 이미지에서 읽은 것이거나, 본문이 길이 제한으로 잘렸거나(`truncated`), 본문에 이미지가 있는데 `images_checked`가 false면, 대상이 그곳에 있을 수 있으므로 규칙 1·2를 적용하지 않고 `unknown` / `missing`으로 둔다. evidence에 추정하지 않은 이유를 모두 쓴다. 공지에 적힌 대상(text_quote 등)은 첨부가 있어도 그대로 쓴다.
12. **판정 범위 밖 조건 [결정 2026-11-21, 결정 2 (C)]** — `other_conditions`는 판정 필드가 아니다. `text`가 공백뿐인 항목은 뺀다. 각 조건의 근거는 2~5번과 같이 확인해 `source`를 붙여 출력의 `other_conditions`로 돌려준다.

## 4. 판정 집계

순서대로 적용한다.

1. `source = text_quote`인 필드에 `mismatch`가 하나라도 있으면 → **불가**
2. 그 외에 `source = image_read`인 필드에 `mismatch`가 있으면 → **확인 필요** (이미지 유래 불가는 낮춘다) **[결정]**
3. `unknown`이 하나라도 있거나, 평가 가능한 필드가 하나도 없으면 → **확인 필요**
4. `other_conditions`가 하나라도 있으면 → **확인 필요** (코드가 확인할 수 없는 조건이다) **[결정 2026-11-21]**
5. 그 외 → **가능** (이미지 유래 값으로 `match`한 경우도 가능으로 두되 신뢰도 표시) **[결정]**

`apply_start`는 "아직 신청 전" 안내에만 쓰므로, null이거나 검증에 실패해(`unknown`) 판정에서 무시하고 `reasons`에만 표시한다. `apply_end`가 `unknown`(null·검증 실패)이면 3번에 따라 "확인 필요"다. [제안]

**confidence**
- 판정이 "불가"면 `verified`다. "불가"는 본문 인용으로 확인된 불일치로만 나오기 때문이다. [제안]
- `verified`: 모든 근거가 `text_quote`
- `image_unverified`: 하나라도 `image_read`가 판정에 쓰임
- `partial`: 하나라도 `missing`·`unverified_quote`·`unrecognized_value`가 있음 (`image_unverified`와 함께면 `image_unverified` 우선). 이 경우 보통 verdict가 "확인 필요"다.
- `assumed`: 위 셋이 아니고, 하나라도 `assumed`가 있음(공지에 적혀 있지 않은 대상을 3절 11번으로 채움). [제안]
- 신뢰도를 정할 때는 판정 필드와 함께 `other_conditions`의 근거도 본다(이미지면 `image_unverified`, 확인되지 않은 인용이면 `partial`).

## 5. 출력

```
verdict      "가능" | "불가" | "확인 필요"
confidence   "verified" | "image_unverified" | "partial" | "assumed"
reasons      [{ field, result, source, evidence }]   # evidence = 사용한 인용 또는 "이미지에서 읽음" 또는 사유 문장
deadline     { date, d_day }  또는 null              # d_day = (apply_end - today).days
other_conditions [{ text, source, evidence }]       # 판정에 넣지 않은 자격 조건(3절 12번)
attachment_status "none" | "not_read"              # 첨부 없음 / 첨부가 있지만 읽지 않음
answer_guide     문자열                               # 학생에게 답할 때 지킬 표현 수준
```

- **답변 표현은 판정 수준을 넘지 않는다 [결정 2026-11-26]**: `answer_guide`는 판정별 문장이다. "가능"은 근거와 마감일을 함께, "불가"는 사유를 근거와 함께, "확인 필요"는 가능을 암시하는 표현("할 수 있다", "해당될 것 같다")을 쓰지 않고 확인할 것과 확인할 곳을 전한다. 추정이 들어간 판정("불가" 제외)은 신뢰도와 관계없이 추정임을, 이미지에 기댄 "가능"(`image_unverified`)은 확정이 아니며 원본 이미지를 확인하라는 것을, 첨부가 있으면 첨부 확인을 덧붙인다.

- **범위 밖 조건의 최종 판단 [결정 2026-11-21]**: 서버는 "확인 필요"와 조건 목록만 돌려준다. 학생이 대화에서 이미 밝힌 정보로 판단할 수 있으면 호스트 AI가 그 조건에 대해서만 판단해 알리고, 없으면 직접 확인하도록 안내한다. 나이·소득 같은 정보를 먼저 묻지 않는다(밝히기 싫을 수 있고, 대화 기억에 남아 다른 대화에 끼어들 수 있다). 이 안내는 도구 설명에 둔다.

- 오류(필수 프로필 누락, 학과 정식명 아님, `grade`·`status` 범위 밖, `extraction`의 빈 목록, 본문 조회 실패)는 `ToolError` 계열로 낸다. 판정을 지어내지 않는다.
- 이미지 유래 값이 판정에 쓰이면 `reasons`에 원본 확인을 안내하는 문구를 넣는다.

## 6. 한계 (보장하지 못하는 것)

- **[한계]** 서버는 인용이 본문에 **있는지**만 확인한다. 그 인용이 value를 **뒷받침하는지**는 검증하지 못한다. 3절 9번은 날짜에 한한 부분 방어다.
- **[한계]** 이미지에서 읽은 값은 틀릴 수 있고, 서버는 그것을 알아낼 수 없다. 그래서 "불가"를 내리지 않고 신뢰도를 표시한다.
- **[한계]** `"ANY"`(제한 없음)는 인용이 있어도 AI의 해석이다.
- **[한계]** 서버는 AI가 이미지를 정말 읽었는지(`images_checked`) 확인할 수 없다. 그래서 이 경우의 "가능"은 신뢰도를 낮춰 확정이 아니라고 표시한다.
- **[한계]** 3절 11번은 "적혀 있지 않음"과 "AI가 읽지 못함"을 구분하지 못한다(둘 다 null). AI가 대상 문장을 놓치면 잘못된 "가능"이 나올 수 있다. 그래서 `assumed`로 표시하고 근거에 추정임을 쓴다. 이 비율은 50건 평가에서 잰다.
- **[한계]** 날짜 교차 검증(C)은 본문의 날짜가 맞는 날짜인지(신청 마감인지 행사일인지)를 구분하지 못한다. 후보 집합에 있는지만 본다.
- **[한계]** 학과·학년·상태를 공지가 자연어로 어떻게 쓰든 AI가 구조로 바꾼다. 이 변환의 정확도는 G3에서 측정하기 전에는 모른다.
