# 판정 명세 — `evaluate_eligibility`

> 2026-10-18 초안 · 확정 아님. 구현 전 확정용이며, 테스트 담당이 이 문서만으로 테스트를 쓸 수 있게 한다.
> 표기: **[결정]** 팀장이 정함(2026-10-18) / **[제안]** 초안 값, 바꿔도 됨 / **[한계]** 이 설계가 보장하지 못하는 것
> 근거 설계: 판정은 AI가 아니라 코드가 한다. AI는 공지에서 조건을 뽑기만 하고, 서버가 인용 검증·날짜 계산·프로필 대조를 한다. 불확실하면 지어내지 않고 "확인 필요"로 답한다.

## 1. 함수 구조

```
evaluate(profile, extraction, body, today, posted_on=None) -> Verdict   # 순수 함수. 네트워크 없음. 테스트 대상
evaluate_eligibility(notice_id, profile, extraction)                    # MCP 도구. 본문과 작성일을 서버가 직접 가져오고 오늘 날짜(KST)를 넣어 evaluate 호출
```

- 판정 로직을 순수 함수로 분리해 `today`와 `body`를 테스트에서 직접 넣는다. [제안]
- 도구는 `get_notice`와 같은 방식으로 `notice_id`를 받아 서버가 본문을 다시 가져온다. 호스트 AI가 넘긴 본문은 쓰지 않는다. [제안]
- **위치**: 판정 코드는 이 리포(`mjc_connector`)의 파이썬 패키지 `mjc_connector`에 둔다. 공지 조회 같은 MCP 도구는 `hackathon_mjc_mcp`를 특정 커밋에 고정한 의존성으로 가져다 쓴다. 원격 진입점도 이 리포로 옮긴다. **[결정 2026-10-23]**
- **입력 형태**: `profile`·`extraction`은 Pydantic 모델(`Profile`, `Extraction`)로 받는다. MCP 입력 스키마와 필드 설명이 자동으로 만들어진다. 모델 검증에서 걸린 값(범위 밖 학년 등)도 도구가 `ToolError`로 바꿔 돌려주어 T18·T19·T24·T25의 오류 규칙을 지킨다. **[결정 2026-10-23]**
- **`posted_on`**: 공지 작성일. 선택 인자로 지금 시그니처에 넣는다. 날짜 연도 보완(3절 9번 C)에 쓰며, 실제로 쓰는지는 dh-11에서 확정한다. **[결정 2026-10-23]**
- **테스트**: 판정 함수를 구현하는 사람(팀장)이 7절 표의 테스트를 먼저 쓰고, 테스트 담당은 표와 대조해 빠진 케이스를 보강한다. **[결정 2026-10-23]**

## 2. 입력

**profile** — 호출 인자로만 받고 저장·로그·캐시하지 않는다.
- `department`: 정식 학과명(문자열). 약칭 정규화는 학과명 매칭 도구(아직 없음)의 몫이고 이 함수는 정식명만 받는다. 정식명 목록은 기존 `list_departments`의 정적 매핑이다. `extraction.departments`도 정식명이어야 한다.
- `grade`: 정수(1~4). 범위 밖이면 `ToolError`.
- `status`: 허용 값 `재학` / `휴학` / `졸업예정` 중 하나. 이 밖의 값은 `ToolError`. **[결정 2026-10-18]** 초기 목록이며 G3(공지 30건 라벨링) 결과를 보고 확정한다. `extraction.statuses`도 같은 값만 쓰고, 공지의 표현이 이 밖이면(복학생, 편입생 등) 호스트 AI가 옮기지 못해 `unknown`이 된다.

**extraction** — 호스트 AI가 공지에서 뽑은 값. 각 필드는 아래 형태다.

| 필드 | value | 설명 |
|---|---|---|
| `grades` | 정수 목록 또는 `"ANY"` 또는 null | 대상 학년 |
| `departments` | 학과명 목록 또는 `"ANY"` 또는 null | 대상 학과 |
| `statuses` | 문자열 목록 또는 `"ANY"` 또는 null | 대상 재학 상태 |
| `apply_start` | `YYYY-MM-DD` 또는 null | 신청 시작 |
| `apply_end` | `YYYY-MM-DD` 또는 null | 신청 마감(당일 포함) |

각 필드의 근거 표기는 다음 중 하나다.
- `quote`: 공지 본문 원문 인용(문자열)
- `from_image: true`: 이미지에서 읽은 값(인용 검증 불가)
- `"ANY"`(제한 없음)도 반드시 `quote`가 있어야 한다(예: "전 학년 대상"). 근거 없는 `"ANY"`는 인정하지 않는다. **[결정 2026-10-18]**

value가 null이면 "못 찾았다"는 뜻이다.

## 3. 필드별 평가

각 필드는 `result ∈ {match, mismatch, unknown, not_yet}`과 `source ∈ {text_quote, image_read, missing, unverified_quote, unrecognized_value}`를 낳는다.

1. value가 null → `unknown` / `missing`
2. `quote`가 있고 본문에 있음 → 값 사용, `source = text_quote`
3. `quote`가 있는데 본문에 없음 → 값을 믿지 않고 `unknown` / `unverified_quote`
4. `from_image: true` → 값 사용, `source = image_read`
5. 값은 있는데 `quote`도 `from_image`도 없음(`"ANY"` 포함) → 3과 같이 `unknown` / `unverified_quote`
6. `"ANY"`에 `quote`가 있고 본문에 있음 → `match` / `text_quote`
7. 인용 비교는 **공백·줄바꿈을 모두 제거하고** NFKC 정규화한 뒤 부분 문자열로 비교한다. [제안]
8. 날짜: `apply_end < today` → `mismatch`. `apply_end == today`는 `match`(당일 포함). `apply_start > today` → `not_yet`(판정에 영향 없음, 사유에만 표시). [제안]
9. **날짜 교차 검증 — 목표는 C, 안 되면 B [결정 2026-10-18]**
   - **C(목표)**: 서버가 본문에서 날짜 표현을 직접 추출해 후보 집합을 만들고, `apply_start`·`apply_end`의 월·일이 그 집합에 있어야 한다. 없으면 3과 같이 `unknown` / `unverified_quote`. 연도가 본문에 없으면 공지 작성일의 연도(작성일 이전 날짜면 다음 해)를 쓴다. [제안]
   - **B(후퇴)**: C를 못 쓰게 되면, 인용 문자열에 값의 월·일 숫자가 들어 있어야 한다(`11월 6일`, `11.6`, `11/06`, `2026-11-06` 허용). 없으면 같은 처리.
   - **후퇴 기준**: 날짜 추출기가 G3로 라벨링한 텍스트 공지에서 정답 날짜를 후보에 포함하는 비율이 임계값에 못 미치면 B로 한다. 임계값은 G3 결과를 본 뒤 팀장이 정한다. [제안: 기준 방식만, 값은 미정]
   - C·B 모두 `from_image` 값에는 적용하지 않는다(본문에 근거가 없다). 인용(`quote`)이 있는 날짜에만 적용한다.
   - 학년 숫자 교차 검증은 하지 않는다("2학년 이상" 같은 표현 때문). [결정]
10. `departments`·`statuses` 값이 허용 목록(정식 학과명 목록, status enum) 밖이면 값을 사용하지 않고 `unknown` / `unrecognized_value`. 인용 검증보다 먼저 적용한다. 정식 학과명 목록은 기존 `list_departments`의 정적 매핑을 쓴다. [제안]

## 4. 판정 집계

순서대로 적용한다.

1. `source = text_quote`인 필드에 `mismatch`가 하나라도 있으면 → **불가**
2. 그 외에 `source = image_read`인 필드에 `mismatch`가 있으면 → **확인 필요** (이미지 유래 불가는 낮춘다) **[결정]**
3. `unknown`이 하나라도 있거나, 평가 가능한 필드가 하나도 없으면 → **확인 필요**
4. 그 외 → **가능** (이미지 유래 값으로 `match`한 경우도 가능으로 두되 신뢰도 표시) **[결정]**

`apply_start`는 "아직 신청 전" 안내에만 쓰므로, null이거나 검증에 실패해(`unknown`) 판정에서 무시하고 `reasons`에만 표시한다. `apply_end`가 `unknown`(null·검증 실패)이면 3번에 따라 "확인 필요"다. [제안]

**confidence**
- `verified`: 모든 근거가 `text_quote`
- `image_unverified`: 하나라도 `image_read`가 판정에 쓰임
- `partial`: 하나라도 `missing`·`unverified_quote`·`unrecognized_value`가 있음 (`image_unverified`와 함께면 `image_unverified` 우선). 이 경우 보통 verdict가 "확인 필요"다.

## 5. 출력

```
verdict      "가능" | "불가" | "확인 필요"
confidence   "verified" | "image_unverified" | "partial"
reasons      [{ field, result, source, evidence }]   # evidence = 사용한 인용 또는 "이미지에서 읽음" 또는 사유 문장
deadline     { date, d_day }  또는 null              # d_day = (apply_end - today).days
```

- 오류(필수 프로필 누락, 학과 정식명 아님, `grade`·`status` 범위 밖, 본문 조회 실패)는 `ToolError` 계열로 낸다. 판정을 지어내지 않는다.
- 이미지 유래 값이 판정에 쓰이면 `reasons`에 원본 확인을 안내하는 문구를 넣는다.

## 6. 한계 (보장하지 못하는 것)

- **[한계]** 서버는 인용이 본문에 **있는지**만 확인한다. 그 인용이 value를 **뒷받침하는지**는 검증하지 못한다. 3절 9번은 날짜에 한한 부분 방어다.
- **[한계]** 이미지에서 읽은 값은 틀릴 수 있고, 서버는 그것을 알아낼 수 없다. 그래서 "불가"를 내리지 않고 신뢰도를 표시한다.
- **[한계]** `"ANY"`(제한 없음)는 인용이 있어도 AI의 해석이다. 대상 언급이 없는 공지는 "확인 필요"가 되므로 "확인 필요" 비율이 높아질 수 있다.
- **[한계]** 날짜 교차 검증(C)은 본문의 날짜가 맞는 날짜인지(신청 마감인지 행사일인지)를 구분하지 못한다. 후보 집합에 있는지만 본다.
- **[한계]** 학과·학년·상태를 공지가 자연어로 어떻게 쓰든 AI가 구조로 바꾼다. 이 변환의 정확도는 G3에서 측정하기 전에는 모른다.

## 7. 테스트 명세 (테스트 담당용)

`evaluate()`는 순수 함수이므로 아래 표의 입력을 그대로 넣는다. 기본값: `today = 2026-10-20`, `profile = {department: "정보통신공학과", grade: 2, status: "재학"}`, 본문은 아래 문장을 포함한다고 가정한다.

> 본문: `대상: 전 학과 2학년 재학생. 신청기간: 2026.10.15 ~ 2026.10.31. 접수 방법은 학과 사무실 방문.`

특별한 언급이 없으면 나머지 필드는 기본 일치(text_quote)다. **값을 바꾸는 케이스(T02~T06 등)는 본문도 그 값에 맞게 바꾼 변형 본문을 쓴다.** 인용이 실제로 값을 뒷받침해야 하고, 날짜는 본문의 날짜 후보에 있어야 3절 9번을 통과하기 때문이다. 예: T03·T04는 본문의 마감일을 해당 날짜로 바꾼 본문을 쓴다.

| T03 | `apply_end=2026-10-19` text_quote | 불가 | 마감 지남 |

| T15b | `departments="ANY"`, quote `전 학과`(본문에 있음), 나머지 일치 | 가능 | verified |

| T25 | `profile.grade`가 1~4 밖(예: 0, 5) | 오류 | ToolError |

T21·T22는 도구 레벨 테스트이고 나머지는 순수 함수 테스트다. T16·T16b는 날짜 교차 검증 C용, T16c는 B 후퇴용이며 둘 중 채택된 쪽만 쓴다.

## 8. 열린 결정

결정됨 (2026-10-18, 팀장)
1. 날짜 교차 검증: 목표는 C(서버가 본문 날짜를 직접 추출해 대조), 안 되면 B(인용 안의 월·일 확인). 학년은 제외.
2. 근거 없는 `"ANY"`는 인정하지 않고 `unknown`(확인 필요). 인용이 있는 `"ANY"`만 일치.
3. `status`는 재학/휴학/졸업예정 enum으로 시작하고 G3 후 확정.

남은 것
4. 호스트가 `extraction`을 제대로 채우는지는 G1 이후 실제 호출로 확인한다 [미검증]. 방침: G1 연결 직후 공지 5~10건으로 실제 호출해 오류 양상(인용 변형, 인자 오류)을 보고, 문제가 크면 인자를 단순화한다(인용을 마감일·학년에만 필수로 줄이는 안).
