# 개발 절차서 (팀원용)

> 2026-10-18 초안 · 확정 아님. 대상: 서브 개발·테스트 담당 팀원.
> 표기: **[확인]** 리포에서 직접 확인 / **[제안]** 팀장 확인이 필요한 정한 값.
> 구체적인 작업은 `작업카드/`를 본다. 일정은 팀장이 따로 공유한다. 이 문서는 "어떻게 일하는가"만 다룬다.

## 1. 작업 대상

- 리포: `https://github.com/4thIS/hackathon_mjc_mcp.git` (기존 MCP 서버). 11/6까지의 공지·학사일정·테스트 작업은 모두 여기서 한다. [확인: origin 주소] 새 리포 구조는 아직 결정되지 않았다.
- 시작 기준 브랜치는 `origin/main`이다. 팀장의 원격 서버 커밋(Dockerfile 등)은 로컬 브랜치에만 있어 팀원 리포에는 없다. 카드가 그 파일을 건드리라고 하지 않는 한 신경 쓰지 않아도 된다. [확인]

## 2. 환경 준비

```bash
git clone https://github.com/4thIS/hackathon_mjc_mcp.git
cd hackathon_mjc_mcp
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt   # macOS/Linux는 .venv/bin/python
.venv/Scripts/python -m pytest tests/ -q
```

- 마지막 명령이 **106 passed**여야 시작할 수 있다. 근거: 2026-10-18 팀장 PC의 로컬 브랜치에서 실행해 106 passed를 확인했고 [확인], 그 브랜치와 `origin/main`의 `tests/`는 동일하다 [확인]. 다만 `origin/main`을 clone해 직접 돌린 결과는 아니다 [미검증]. 숫자가 다르면 작업 전에 팀장에게 알린다.
- 학교 로그인이 필요한 도구(`search_courses`, `get_syllabus`)와 `auth/login_helper.py`는 이번 작업에 쓰지 않는다.

## 3. 한 작업의 흐름

1. 카드를 읽는다. 모르는 용어나 범위가 불분명하면 **코드를 쓰기 전에** 팀장에게 묻는다.
2. `origin/main`에서 브랜치를 만든다. 이름은 `feature/<핸들>-<주제>`. [제안] (리포에는 `feature/`, `docs/`, `fixtures/` 접두 관행이 있다 [확인])
3. **테스트를 먼저 쓴다.** 새 동작을 검증하는 테스트가 실패하는 것을 확인한 뒤 구현한다.
4. 구현한다. 카드의 "건드리지 말 것"은 수정하지 않는다.
5. `pytest tests/ -q` 전체를 돌려 기존 테스트가 하나도 깨지지 않았는지 확인한다.
6. PR을 올린다. **PR 하나는 카드 하나**다. 본문에 카드 이름, 바뀐 것, 테스트 결과(예: `112 passed`)를 적는다.
7. 팀장이 리뷰하고 병합한다. 팀원은 `main`에 직접 push하지 않는다. [제안]

완료 기준은 카드의 체크리스트 전부 + 전체 테스트 통과다. "돌아가는 것 같다"는 완료가 아니다.

## 4. 코드 규칙 (어기면 서버가 깨진다) [확인: 리포 CLAUDE.md]

- 어디서든 `print()` 금지. stdout은 MCP 통신 채널이다. 로그는 `logging`(stderr)만.
- HTTP 응답은 `resp.text`가 아니라 bytes(`resp.content`)로 받고, 인코딩 판단은 `common/parse.py`에서만 한다.
- 요청은 `common/http.py`의 `fetch()`로만 한다. 같은 호스트에 1초 간격이 강제된다. 타임아웃과 `follow_redirects=False`를 지킨다.
- 에러는 `common/errors.py`의 `ToolError` 계열을 쓴다. 원문 HTML·헤더·쿠키를 에러에 담지 않는다.
- 도구 반환값은 dict가 아니라 Pydantic `BaseModel`이다. 필드마다 `Field(description=...)`을 쓴다.
- 도구 등록 방식과 `register()`는 건드리지 않는다. 팀장이 같은 줄을 수정하는 브랜치가 있어 충돌한다. [확인: `title=` 커밋이 `register()`를 바꿨다]
- 테스트 fixture는 실제 응답을 **bytes 원본**으로 저장한다(텍스트로 저장하면 인코딩 버그가 숨는다).

## 5. 커밋과 푸시

- 이 리포는 `git commit`/`git push`마다 본인 승인이 필요하다. [확인: `.claude/settings.json`의 `ask` 규칙]
- 메시지 형식은 `<type>: <한국어 제목>`이다. type은 `feat`·`fix`·`docs`·`test`·`refactor`·`chore` 중 하나. [확인: 기존 커밋 관행]
- 변경이 크면 본문에 글머리표로 적는다. 이슈 번호가 있으면 본문 끝에 `Closes #번호`.

## 6. 하지 않는 것

- 로그인 필요 도구, `auth/`, `common/session.py` 수정. 세션 쿠키·비밀번호를 코드·테스트·로그·PR에 넣는 것.
- 학교 사이트를 테스트용으로 반복 호출하는 것. 필요한 실제 응답은 **한 번만** 받아 fixture로 저장하고, 이후는 fixture로 테스트한다.
- 요청 간격(1초) 제한을 우회하거나 동시 호출로 부하를 주는 것.
- 비밀값이 들어간 파일(`.env`, 키, 토큰)을 만들거나 커밋하는 것. 필요하다고 느끼면 먼저 팀장에게 묻는다.
- 카드에 없는 개선. 발견한 문제는 PR에 넣지 말고 팀장에게 알린다(별도 카드가 된다).
